# pdf-viewer

Shows a pdf the app already holds in memory, built on `pdfjs-dist`. The counterpart of
[pdf-builder](../pdf-builder/README.MD), which writes one.

## Usage

```html
<template>
    <PdfViewer :data="bytes" @error="onError" />
</template>

<script lang="ts" setup>
import PdfViewer from '@stamhoofd/frontend-pdf-viewer/PdfViewer.vue';
</script>
```

- `data` is a `Uint8Array` of pdf bytes, never a url: the documents we show are fetched by the app
  and have no url of their own. The viewer copies the bytes before handing them to pdf.js, which
  would otherwise transfer the buffer to its worker and leave the caller with an empty array.
  Assigning a new array reloads the document.
- `error` fires once when the document cannot be opened at all. The viewer shows its own error box
  in that case, so listening is optional. A single page that fails to paint reports inside that page
  and does not fire this.

The viewer fills the width it is given and lays its pages out as a column. The parent decides the
width and does the scrolling; there is nothing else to configure.

## How it holds up on a long document

Most documents we show are a single page, but nothing may assume that.

- Every page takes its place in the scroll height from the start, using the size of the first page
  until it has been loaded itself. The scroll position therefore does not jump while reading.
- A page is rendered when the reader comes near it and dropped again once it is well out of view,
  which is what keeps the canvas memory of a long document inside what a phone will give us.
- A page is rendered to fit the width of the viewer at the pixel density of the screen, capped at
  the largest canvas browsers reliably allocate. See `getRenderScale.ts`.

## Two things pdf.js makes easy to get wrong

- **The worker is bundled, not referenced by url.** pdf.js ships it as `pdf.worker.min.mjs`, and a
  static host that serves `.mjs` as `application/octet-stream` makes the browser refuse the module
  script; pdf.js then falls back to its fake worker and never opens the document. The viewer also
  hands pdf.js the port itself rather than going through `GlobalWorkerOptions`, so importing
  `@stamhoofd/pdf-parse` — whose worker module sets `globalThis.pdfjsWorker` at module scope —
  cannot drag rendering onto the main thread.
- **No `AbortSignal.any` polyfill is needed here, until someone adds a text or annotation layer.**
  pdf.js 6 calls it, but only from its annotation editor and its touch manager, neither of which
  the viewer mounts. That matters because the app still supports Safari 15.4 and `AbortSignal.any`
  arrived in 17.4. Mount any of those layers and this package needs the polyfill; a test fails the
  moment a render reaches for it.

## Tests

`pnpm stam test pdf-viewer`, in vitest browser mode because the whole point is a real canvas. The
fixture pdf is generated by `src/tests/createTestPdf.ts`, so no real document is ever committed.
